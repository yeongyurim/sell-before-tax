**최적화 품질** — 여유 시나리오에서 연간 실현손익을 **2,499,798원**에 착지시킵니다.

## 계산이 서버로 가지 않습니다

보유 종목·매입단가는 민감 금융정보이므로 **모든 세금 계산과 최적화는 브라우저에서만** 실행됩니다.
API 라우트·데이터베이스·외부 시세 연동·로그인이 전혀 없으며, 빌드 결과는 정적 페이지 하나입니다.

## 도메인 규칙

| 항목 | 값 |
|---|---|
| 과세 대상 | 해외 상장 주식·ETF 양도차익 |
| 과세 기간 | 1/1 ~ 12/31 (결제일 기준) |
| 기본공제 | 연 250만원 |
| 세율 | 양도소득세 20% + 지방소득세 2% = 22% |
| 손익통산 | 같은 과세기간 내 해외주식 간 이익·손실 합산 |
| 이월결손금 | 공제 없음 |

```
realizedTotal = priorRealizedGain + Σ (x_i × perShareGain_i)
taxableBase   = max(0, realizedTotal - 2_500_000)
tax           = taxableBase × 0.22
```

원화 기준 과세이므로 환차익도 과세 대상입니다.

```
perShareGain_i = (currentPrice_i × fxSell) - (avgBuyPrice_i × fxBuy_i)
```

기본값은 `fxBuy = fxSell = 현재 환율`(단일 환율)이며, 표에서 **매수 시점 환율 직접 입력**을 켜면
종목별 매수 환율을 넣어 환차손익까지 반영할 수 있습니다.

## 왜 단순 정렬로는 안 되는가

기본공제 250만원 때문에 세금 함수가 구간 선형입니다. 실현손익이 250만원 이하면 한계세율이 0이고,
넘는 순간 22%가 됩니다. 따라서 "수익률 낮은 순"이나 "손실 종목 우선" 같은 단일 기준 그리디는
최적해를 놓칩니다. 이익 종목과 손실 종목을 **함께** 조합해 실현손익 합계를 공제 한도 근처에
착지시키는 것이 핵심입니다.

여유 시나리오 기준 — 단순 매도는 세금 4,770,392원, 최적 조합은 0원입니다.

## 세금이 갈리지 않을 때

상계 여유가 충분하면 세 조합이 전부 같은 세금(대개 0원)으로 수렴합니다. 이때 세금은 더 이상
선택 기준이 못 되므로, `hasUniformTax()`가 참이면 화면이 다음처럼 바뀝니다.

- 안내 문구를 띄워 이제 무엇을 보고 골라야 하는지 알린다
- 카드의 주 지표를 **예상 세금 → 포트폴리오 유지율**로 교체하고, 세금은 보조 지표로 내린다
- 단순 매도 유지율과의 대비를 함께 보여준다 (여유 시나리오에서 69.1% → 93.7%)

## 해결한 문제

구현하면서 판단이 필요했던 두 지점입니다.

### 1. 필요 이상으로 파는 퇴화해

**문제** — 목표 금액만 채우면 되는데, 최적해라고 나온 조합 중에 필요보다 훨씬 많이 파는 것들이
섞여 나왔습니다. 세금은 똑같이 0원인데 주식은 더 많이 팔린 상태입니다. 사용자 입장에서는
명백히 손해인 답이 "최적"으로 제시되는 셈입니다.

**원인** — 기본공제 250만원 구간 안에서는 세금 함수가 평평합니다. 실현손익이 한도 밑이면
얼마를 팔든 세금이 0원이므로, 세액이 동일한 해가 사실상 무수히 많습니다. 당시 목적함수는

```
cost = tax + portfolioWeight × DRIFT_SCALE × portfolioDrift
```

뿐이라 이 해들을 구별할 근거가 없었고, `portfolioWeight = 0`(세금 최소)일 때는 drift 항마저
사라집니다. 국소탐색은 그중 먼저 만난 아무 해에서나 멈춥니다. 알고리즘의 버그가 아니라
**목적함수가 선호를 표현하지 않아서** 생긴 문제였습니다.

**대응** — 초과 매도 금액에 비례하는 항을 목적함수에 추가했습니다.

```
cost = tax + portfolioWeight × DRIFT_SCALE × portfolioDrift + ε × (초과 매도 금액)
```

계수는 `EXCESS_CASH_PENALTY = 1e-9`입니다 (`lib/optimizer.ts`). 이 크기를 고른 이유는
**세액 최적성을 건드리지 않기 위해서**입니다. 1e-9는 1원의 세금 차이도 뒤집지 못하므로
세금이 다른 두 해의 순서는 절대 바뀌지 않고, 세금이 완전히 같을 때만 "덜 파는 쪽"을 고르는
동점 해소 장치로만 작동합니다. 벌점을 크게 잡으면 세금을 더 내더라도 덜 파는 해를 고르기
시작하므로, 의도적으로 세액 차이의 최소 단위보다 작게 잡았습니다.

### 2. 최적화가 기존 방식보다 나쁠 수 있음

**문제** — 최적화 로직을 붙였다고 해서 항상 이득이라는 보장이 없었습니다. 어떤 입력에서는
그냥 수익률 높은 순으로 파는 단순 매도가 더 나은 결과를 낼 수 있습니다. 절세 도구를 썼는데
안 쓴 것보다 손해라면 서비스로서 성립하지 않습니다.

**원인** — 2단계 국소탐색은 steepest-ascent hill climbing이라 초기해 주변의 국소 최적에
갇힙니다. 초기해 3종(`greedyLossFirst`, `greedyDeductionFit`, `greedyProRata`)이 모두
단순 매도보다 못한 골짜기에 떨어지면 최종 결과도 그보다 못합니다. 랜덤 재시작 3회를 돌려도
확률을 높일 뿐 보장은 되지 않습니다.

**대응** — 탐색 기법을 바꾸는 대신, **단순 매도 결과 자체를 네 번째 초기해로 투입**했습니다
(`lib/optimizer.ts`의 `seeds` 배열).

```ts
const seeds = [
  greedyLossFirst(ctx),
  greedyDeductionFit(ctx),
  greedyProRata(ctx),
  buildBaselineLots(input),   // 단순 매도
];
```

탐색은 초기해 집합 중 **최선**에서 출발해 비용이 낮아지는 방향으로만 이동합니다. 따라서 최종
해의 비용은 정의상 baseline 이하이고, 절감액이 음수가 되는 경우가 원리적으로 없어집니다.
탐색을 더 정교하게 만드는 대신 **하한선을 후보에 포함시켜** 보장을 만든 선택입니다.

`lib/optimizer.test.ts`가 고정 시드로 무작위 포트폴리오 12건을 생성해
`plans[0].tax <= baseline.tax`를 검증합니다.

## 알고리즘

**1단계 · 초기해 4종** (`lib/optimizer.ts`)

| 이름 | 전략 |
|---|---|
| `greedyLossFirst` | 평가손실 종목 전량 매도 → 부족분을 주당이익 낮은 순으로 |
| `greedyDeductionFit` | 실현손익 합계를 남은 공제 한도에 맞춤 (매도대금 1원당 이익이 작은 순) |
| `greedyProRata` | 현재 비중대로 균등 비율 매도 (drift 최소) |
| `baseline` | 단순 매도. 최적해가 baseline보다 나빠지지 않도록 초기해에 포함 |

**2단계 · 국소탐색** — steepest-ascent hill climbing. 이웃은 (a) 한 종목 수량 ±1/±5/±10/±5%
(b) 두 종목 간 매도 금액을 유지한 수량 교환. 시간 예산 200ms 또는 최대 5,000회 이동, 랜덤 재시작 3회.
난수는 고정 시드라 같은 입력이면 항상 같은 결과가 나옵니다.

**3단계 · 결과 선별** — `portfolioWeight`를 0 / 0.5 / 1로 각각 돌려 "세금 최소 / 균형 / 비중 유지"
세 조합을 만듭니다. 완전히 같은 조합은 하나로 합칩니다.

목적함수:

```
cost = tax + portfolioWeight × DRIFT_SCALE × portfolioDrift + ε × (초과 매도 금액)
```

`DRIFT_SCALE = targetCash × 0.1`. 마지막 항은 세액이 같은 해가 여럿일 때 "덜 파는 쪽"을 고르게 하는
동점 해소 장치이며, 1원의 세금 차이도 뒤집지 못할 만큼 작습니다(`1e-9`).

`portfolioDrift`는 매도 전후 비중 벡터의 L1 거리 절반이고, 전량 청산이면 1입니다.
